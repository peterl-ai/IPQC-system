# Isolated Android 11 enrollment feasibility gate

This directory is separate from the future patrol application. No production Android app, APK, signing key or authority-bearing credential is delivered here. Local feasibility execution is **SKIPPED**: Android SDK/adb/Gradle/JDK and an SM-T500 are unavailable on the implementation host. Backend development and software DER/JOSE interoperability tests proceed independently. Do not describe them as hardware/Keystore PASS.

## On-site preparation

1. Use a spare Samsung Galaxy Tab A7 **SM-T500 on Android 11 / API 30**, isolated test Wi-Fi and synthetic device/line records. Record model, API level, OS build/security patch and probe source commit. Record SDK/JDK/Gradle versions when installed. Use a disposable development workstation and an independently named probe package such as `com.jaxpower.ipqc.enrollmentprobe`; minSdk 30. Never reuse a future production package/signing identity.
2. Create a minimal local Android Studio Empty Activity project for that probe only. Add no patrol UI, device administrator, authentication shortcuts, NativeSession or OfflineGrant. Use local debug signing, keep all generated keystores/build output outside Git, and record APK SHA-256/source commit. Install via USB with site approval; confirm device model/API with `adb shell getprop ro.product.model` and `adb shell getprop ro.build.version.sdk`.
3. IT supplies an **isolated Development** Bootstrap HTTPS URL, trusted test server chain and dedicated disposable issuer PFX outside the repository. Keep normal TLS hostname/chain validation enabled; no trust-all TrustManager, disabled hostname verification or HTTP fallback. Configure the backend according to `docs/13_DEVICE_ENROLLMENT.md`; production Bootstrap remains disabled. The future production CA and Native mTLS host are separate, unexecuted gates.

## Keystore and wire procedure

4. In the probe, use `KeyPairGenerator.getInstance("EC", "AndroidKeyStore")` with `KeyGenParameterSpec.Builder(alias, KeyProperties.PURPOSE_SIGN | KeyProperties.PURPOSE_VERIFY)`, `.setAlgorithmParameterSpec(new ECGenParameterSpec("secp256r1"))`, `.setDigests(KeyProperties.DIGEST_SHA256)`. Do not request StrongBox as a mandatory condition; record actual support/security level. Never silently substitute a software/exportable provider. Generate once and reload by alias after process restart. Verify `privateKey.getEncoded()` is null, provider is AndroidKeyStore, public SPKI is P-256 and `KeyFactory.getKeySpec(privateKey, KeyInfo.class).isInsideSecureHardware()` result is recorded. This observation is not remote attestation or proof against a compromised OS.
5. Build one signed PKCS#10 DER CSR with subject `CN=IPQC-{DeviceId}`, using that exact Keystore private key with SHA256withECDSA. A vetted PKCS#10 builder may be needed; do not use hidden Android APIs or export the private key. **Persist original CSR bytes in app-private storage** and compute SHA-256 of CSR and SPKI as uppercase hex. Regenerating a signed CSR on retry changes CSR hash. The CSR builder/library choice and successful API-30 build are part of the outstanding feasibility evidence.
6. Admin issues an invitation through Web for the synthetic pending reserved device. Deliver the single-use secret in person through the isolated probe input; do not capture it in logs, screenshots, URLs or Git. Probe posts `{ invitationSecret, csrDerBase64 }` to the challenge route.
7. Verify/display the decoded server DeviceId, LineId, environment, source/target binding versions, CSR/SPKI hashes and expiry. Sign **the ASCII encoded header + dot + encoded payload without reserialization** with `Signature.getInstance("SHA256withECDSA")` initialized with the Keystore private key. DER signature must be converted to 64-byte R||S as defined in `docs/13_DEVICE_ENROLLMENT.md` (strict positive integers, optional DER sign-byte removal, each padded to 32 bytes). Send compact Base64url JWS with no `=` padding. Save only public challenge/proof test artifacts in a restricted test evidence folder; invitation/nonce/proof artifacts are transient and must not go into repository/audit logs.
8. Required interoperability evidence: genuine Keystore proof accepted by ASP.NET as PendingApproval; direct DER JWS rejected; 63/65-byte raw signature, ES384/none headers, altered environment/line/version, wrong CSR key and replay rejected. Test cases whose inputs are manually generated by desktop OpenSSL are software tests, not Keystore tests. At least one SM-T500 R or S requiring a DER sign byte and one requiring left padding should be captured as public format vectors, with no private material. Retry fresh challenges within rate limits to obtain edge vectors.
9. Admin physically compares the PAD-displayed stable IDs, environment, N/N+1 and full CSR/SPKI fingerprints to Web, then explicitly acknowledges verification and approves. Poll with a fresh Receipt-purpose key proof; expect IssuedUnconfirmed candidate. Verify leaf SPKI matches the persistent key, SAN device/credential identity, clientAuth EKU, CA=false and test chain. Repeated receipt/recovery returns identical PEM and operation ID. Restart probe process and reload the same key/CSR; repeat a fresh receipt proof. Do not replace the AndroidKeyStore entry with the candidate certificate in this phase; installing an operational client identity belongs to P1-03B.
10. Cancel, revoke, rebind and replace test records, including while issuance is delayed. Old request/candidate remains associated with original DeviceId/LineId/N+1, is terminal/revoked and never transferred. RegisteredDevice remains NotEnrolled, BindingVersion unadvanced by enrollment, CanExecuteLineShared false. Prove candidate/proof/device ID alone cannot call existing protected APIs; JWT/ownership/workflow checks remain authoritative.

## Required signed-off evidence and cleanup

- PAD operator: model/API/build, APK/source/toolchain hashes, exact provider and non-exportability observations, hardware-backed result (truthfully recorded), restart/reload results, successful real Keystore -> ASP.NET proof, negative-format/replay cases, and public CSR/SPKI/certificate hashes.
- Admin: synthetic DeviceId/LineId, source/target versions, fingerprint comparison, approval/cancellation ChangeIds, truthful Admin/ApplicantKey/System audit. There must be **no Device actor** and no Enrolled/Current status in A.
- IT: isolated HTTPS hostname/chain validation, test CA/public root fingerprint, external receipt-volume persistence and restart recovery, delayed issuance/revocation results, no production key/cert access, and production Bootstrap disabled. Production CA integration, real mTLS, proxy identity spoofing tests, CRL/OCSP and database-authoritative activation remain P1-03B gates.
- Database owner: disposable PostgreSQL fresh and populated upgrade, constraints and concurrent provisioning/enrollment/lease tests. Generated SQL and SQLite PASS do not establish a PostgreSQL runtime PASS.
- Remove the probe alias/app and revoke all test candidates, destroy invitation material and disposable test CA private key under site procedure, retain only sanitized public evidence. Do not commit APKs, debug/production signing keys, private keys, real staff/device inventories or invitation secrets.

Sources: [Android Keystore](https://developer.android.com/privacy-and-security/keystore), [KeyGenParameterSpec](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec), [ES256 wire format](https://www.rfc-editor.org/rfc/rfc7518.html#section-3.4). Hardware backing must be measured on the actual PAD; it is not assumed from the model name.
