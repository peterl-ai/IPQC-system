# P1-03A candidate device enrollment

Implementation reference, subordinate to approved Architecture Rev3.1 and the binding Implementation Handoff (including F2). Neither authority is amended here.

## Security boundary

This phase proves possession of an applicant public key, records explicit Admin approval, and obtains an **unconfirmed candidate** certificate. It does not authenticate a PAD. `RegisteredDevice.Status` remains `PendingCredential`, `CredentialStatus` remains `NotEnrolled`, and `CanExecuteLineShared` remains false. Enrollment does not change Device Revision, LineId or BindingVersion. The captured source reservation N and target credential N+1 are immutable request facts; N+1 is not an effective binding in this phase.

There are no Native endpoints, mTLS listeners, proxy certificate headers, NativeSession, OfflineGrant, shared drafts, LineShared activation or Submit changes. Existing JWT/RBAC and legacy workflow restrictions still apply. Sending a candidate certificate, device ID, reservation or signed enrollment proof cannot grant patrol authority.

Bootstrap routes default to disabled. Enabling Bootstrap or the development issuer outside `Development` / `Testing` fails application startup, including `Production`. In Development, the actual request must be HTTPS. Testing HTTP is limited to the test host. No forwarded-header middleware or client-supplied transport identity is added. Production must remain disabled until a separately reviewed P1-03B installs and verifies the listener/trusted transport boundary and database-authoritative activation. A caller can generate a software P-256 key: PoP alone does **not** prove Android origin, hardware attestation or a trustworthy device. Physical Admin verification is mandatory.

## Admin and Bootstrap contracts

All Admin endpoints require the existing DevicesRead/DevicesWrite permissions, granted only to Admin. Mutations recheck the current active Admin and forced-password state inside the provisioning transaction. PostgreSQL also holds a shared account-row lock until commit. Disabled/revoked JWTs retain existing 401 semantics; other roles / forced-change users receive 403.

| Endpoint | Input / result |
| --- | --- |
| GET `/api/admin/devices/{deviceId}/enrollments?page=1&pageSize=20` | Paginated request/candidate history; max size 100. No invitation secret, nonce or CSR body returned. |
| POST `/api/admin/devices/{deviceId}/enrollments` | `{ expectedDeviceRevision }`; 200 request, one-time `invitationSecret`, invitation expiry. Requires active line reservation and pending device. |
| POST `/api/admin/enrollments/{id}/approve` | `{ expectedRevision, expectedDeviceRevision, lineId, bindingVersion, csrSha256, spkiSha256, operationId }`; 202 candidate issuance accepted, not device activation. `bindingVersion` is source N. |
| POST `/api/admin/enrollments/{id}/cancel` | `{ expectedRevision, reason }`; 200 terminal request and retained candidate history. Reason required, max 2000 characters. |
| POST `/bootstrap/v1/enrollments/{id}/challenge` | `{ invitationSecret, csrDerBase64 }`; 200 `{ challengeId, protectedHeader, payload, expiresAtUtc }`. No Admin JWT or PAD trust is inferred. |
| POST `/bootstrap/v1/enrollments/{id}/proof` | `{ challengeId, jws }`; 202 `PendingApproval`. Consumes the invitation and challenge atomically. |
| POST `/bootstrap/v1/enrollments/{id}/receipt-challenge` | Empty body; fresh Receipt-purpose challenge for a previously proven request. Does not disclose its result or authorize mutations. |
| POST `/bootstrap/v1/enrollments/{id}/receipt` | Fresh key proof `{ challengeId, jws }`; 200 own request/candidate result, including public PEM when available. Never authenticates a PAD. |

Bodies reject unknown fields and are capped at 32 KiB, including chunked Kestrel requests. CSR DER max 16 KiB, JWS max 24,000 characters. Responses use `Cache-Control: no-store`. Secrets occur only in the one-time Admin response and Bootstrap challenge input, never URLs, DB plaintext, logs or audit. The Web drawer stores a new invitation only in component memory, clears it on dismissal/unmount, and does not use browser storage. Secure delivery to the physically verified intended operator remains an on-site responsibility; no public pairing portal is introduced.

Bootstrap: 20 requests/minute per socket peer IP, no queue; Admin enrollment: 60/minute per authenticated user, no queue (includes list polling); DB challenge budget: 5/minute per enrollment across Enrollment and Receipt purposes. Instance-local IP/user rate limits are not a distributed production abuse boundary. Production Bootstrap is disabled. Invalid token: 401; missing request: 404; malformed CSR/JWS: 400; stale/replayed/expired/version conflicts: 409; body too large: 413; throttled: 429; unconfigured enrollment/PKI: 503. Existing provisioning error codes are retained, with enrollment-specific codes in the JSON `code` field. Web displays a localized safe conflict/error and never automatically repeats a mutation.

Invitation lifetime: 10 minutes. Overall request lifetime: 30 minutes. Challenge lifetime: at most 2 minutes, capped by invitation expiry for Enrollment purpose. Only one nonterminal request per device. IssuedUnconfirmed remains open until cancelled/expired. Reads derive Expired after the deadline; a worker handling a pending issuance or a subsequent invitation records the durable terminal transition and candidate revocation. A stale unconfirmed candidate never gains authority while awaiting cleanup. Receipt-purpose proofs can recover one's own terminal result; they cannot revive it.

## CSR and JWS wire profile

PKCS#10 DER, standard Base64 in JSON; subject exactly `CN=IPQC-{lowercase hyphenated DeviceId}`. CSR signature must verify. Only EC P-256 / `secp256r1` is accepted. The CSR SPKI is the sole proof key; no client JWK or requested certificate extension grants identity. The first valid challenge pins the exact CSR bytes, SHA-256 and SPKI. **Persist and reuse that CSR** for retries: regenerating an ECDSA-signed CSR changes its hash even with the same key.

The server returns already Base64url-encoded `protectedHeader` and `payload`. Sign the ASCII bytes `protectedHeader + "." + payload` using SHA256withECDSA. Return compact JWS `protectedHeader.payload.signature`. Do not decode/reserialize the server JSON. Protected header bytes are exactly `{"alg":"ES256","typ":"ipqc-enrollment+jws"}`. No alternate header serialization, algorithm, `none`, JWK, padding or noncanonical Base64url is accepted.

Signature is **exactly 64 bytes: unsigned, big-endian R (32 bytes) followed by S (32 bytes)**; zero-pad each integer on the left. This is RFC 7518 ES256 / IEEE P1363, not ASN.1 DER. Android `Signature.getInstance("SHA256withECDSA")` returns DER integers: parse exactly two positive minimally encoded integers, reject negatives/zero/oversize/trailing data, remove a required sign byte, then left-pad each to 32 bytes. Base64url without `=` padding. ASP.NET explicitly uses `DSASignatureFormat.IeeeP1363FixedFieldConcatenation`. DER sent directly on the JWS wire is rejected. CSR itself retains its standard DER signature representation.

The signed server payload binds version, purpose (`Enrollment` or `Receipt`), audience/environment, EnrollmentId, DeviceId, LineId, source and target BindingVersion, CSR SHA-256, SPKI SHA-256, ChallengeId, random 256-bit nonce and Unix expiry. DB stores payload and nonce hashes, compares the exact payload and consumed/deadline state, and consumes proofs under the provisioning lock. A correctly signed altered identity/environment/version/purpose is rejected. Reissuing an Enrollment challenge consumes prior Enrollment challenges; Receipt challenges cannot invalidate enrollment proofs. A second signature encoding or valid alternative signature over consumed bytes cannot bypass replay checks.

`EnrollmentInteropTests` executes OpenSSL DER signing -> strict JOSE conversion -> ASP.NET verification and ASP.NET JOSE signing -> DER -> OpenSSL verification. Edge tests include sign padding, leading zero limbs, malformed/negative/oversize/zero/trailing integers. This is independent software interoperability evidence, **not Android Keystore execution evidence**. Real-device interoperability is SKIPPED until the isolated SM-T500 procedure in `android/enrollment-probe/README.md` is performed.

Sources: [RFC 7518 §3.4](https://www.rfc-editor.org/rfc/rfc7518.html#section-3.4), [Android Keystore](https://developer.android.com/privacy-and-security/keystore), [KeyGenParameterSpec](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec).

## Candidate issuance and recovery

`IDeviceCertificateIssuer` is the integration seam. No production IT CA adapter is configured in this PR. Default issuer is unavailable: approval fails closed with 503; existing legacy startup and workflows remain usable. The only implemented issuer is an explicitly opted-in, isolated development/test issuer, with an externally provisioned dedicated CA key. Startup never generates an issuer key.

Candidate profile is server controlled: device CN, SAN URI `urn:ipqc:device:{DeviceId}:credential:{CredentialId}`, CA=false, DigitalSignature, explicit clientAuth EKU. Caller CSR extensions are not copied. Frozen validity starts one minute before approval and ends at min(90 days, issuer expiry). Result validation compares key, subject, SAN, usage/extensions, frozen validity and configured root chain. The isolated candidate validator uses `NoCheck` for revocation; this is **not Native TLS validation** and must not be reused as the P1-03B trust policy. CRL/OCSP, IT hierarchy/intermediates, issuer rollover, identity extraction and live transport testing require separate P1-03B/IT review.

Approval creates one candidate and a stable, unique **issuance operation ID** in a short DB transaction. Admin `operationId` independently makes the same actor/content approval retry return the existing result without a second audit or candidate; different snapshots/keys conflict. The Web retains the exact approval payload and operation ID while its drawer remains open.

Worker protocol:

1. Claim under the same P1-02 transaction protocol; mark OutcomeUnknown **before** contacting the signer, with a 30-second lease and System audit. Commit.
2. Outside all DB transactions/locks, recover original result by stable issuance operation ID. Only definitive NotIssued may invoke Issue with the same operation/profile. Unknown/in-flight must never create a fresh signing operation. Validate returned candidate.
3. Clear EF tracked state, reacquire provisioning transaction, match lease ownership and revalidate device status, line activity/reservation, source BindingVersion and deadline. Persist only IssuedUnconfirmed, or retain a late certificate as Revoked with external cleanup pending. Save audit atomically. Worker retries pending outcomes after five seconds, up to eight operations per tick.

Rebind/unbind/revoke/replace and explicit cancellation terminate the original request inside the existing provisioning transaction, consume its challenges and revoke its candidate. Replacement retains both stable device identities and the original ChangeId correlation. It never transfers CSR, credentials, old work or history. In-flight results are retained against the old device/line/version, then revoked externally. External revocation occurs outside the DB transaction and records completion only after acknowledgement. Audit failure rolls back DB changes; an already published signer receipt remains recoverable after lease expiry. Request cancellation during external work leaves the committed operation unknown for recovery.

Development issuer uses a durable public result journal keyed by operation ID and request hash. Exclusive per-operation OS file locks coordinate processes; write-through, flush, then atomic rename publishes a receipt before returning it. Reopening an issuer instance returns the original PEM; content mismatch is rejected. Revocation writes an idempotent tombstone and prevents later signing. This tombstone is an isolated test mechanism, **not a production CRL/OCSP service**. Use a durable local volume and back it up with DB state. Directory-entry durability after sudden power loss and network-filesystem lock semantics are not certified. Loss of the receipt volume is not safely repaired by issuing again: fail closed and restore/reconcile the original outcome. A future real IT adapter must supply equivalent durable outcome lookup, immutable operation/content association and idempotent cancellation/revocation, including delayed results after cancellation. No external CA call belongs in a DB transaction.

## Development configuration

Only on an isolated Development host, configure `Enrollment__EnvironmentId`, `Enrollment__BootstrapEnabled=true`, `Enrollment__DevelopmentIssuerEnabled=true`, `Enrollment__RootPfxPath`, `Enrollment__RootPassword`, `Enrollment__ReceiptDirectory`. Both paths must be absolute and outside the repository. Supply the password through local secret/environment configuration. Keep the PFX private, restrict its file permissions, and use a dedicated disposable development CA unrelated to production. Do not commit PFX, private PEM, passwords, production certificates or APK signing keys. Default `WorkerEnabled=true`; tests disable the background worker and drive scoped recovery explicitly. Do not turn an existing production instance into Development to bypass the guard.

## Migration and compatibility

`20261109202320_P103ADeviceEnrollment` adds DeviceEnrollments, EnrollmentChallenges and DeviceCredentials. Unique constraints protect one open request per device, approval operation IDs, candidate per enrollment, issuance operation IDs and certificate hashes. Revision concurrency tokens, state/version checks and restrictive foreign keys supplement the provider transaction lock. Audit gains typed actor/device/enrollment/credential references; `ActorUserId` becomes nullable. Existing rows retain their actual UserId/name/time/snapshots and receive Admin kind=1. No fake Guid.Empty system user, fabricated device, candidate or history is backfilled.

SQLite rebuilds the audit table to change nullability/add checks/FKs; PostgreSQL uses native uuid, integer, bigint, boolean and timestamp-with-time-zone DDL. Original audit indexes/rows and P1-02 line-history OR projection remain intact. Fresh SQLite, populated P1-02 full-original-column comparison, prior populated legacy upgrades/reports, FK checks and both-provider snapshot checks are regression gates. Generated PostgreSQL idempotent SQL is reviewed without claiming live execution. Live PostgreSQL migration/concurrency remains SKIPPED without a disposable server.

Before applying to any intended environment, back up and verify restore, review provider SQL and allow the SQLite audit-rebuild maintenance window. No production DB was touched. Operational rollback retains the expanded schema and disables enrollment/worker. Pre-P1-03A binaries map ActorUserId as non-null: their audit queries can fail on System/ApplicantKey rows. An application rollback must retain a compatible typed audit reader or a reviewed compatibility patch; do not deploy an unmodified P1-02 binary as the audit recovery plan, fabricate human users, or rewrite history. Destructive Down is intentionally rejected because it would discard credential and audit history. Use a reviewed forward repair or verified coordinated backup restore. Schema expansion does not rewrite Plans, Tasks, historical reports or approved architecture documents.

P1-03B must install separate Bootstrap HTTPS / Native mTLS transport, trusted proxy boundaries, certificate-chain/EKU/revocation checks and a DB-authoritative confirmation that atomically advances to the still-current device/line/target version. Every Native request must validate current identity, credential, line, binding version and device revocation. An A-phase proof, candidate, old reservation or obsolete credential is never sufficient. NativeSession/OfflineGrant and business execution require their separately approved scopes.
